Learning claims

Three scored lessons teach tracking an obstruction, stand occupancy and a changing departure estimate. Each has briefing, practice, three four-choice checkpoints, evidence-cutoff feedback and debrief. The scene, assistant and history are hidden during each question. Guided demonstration instead runs movement and assistant questions without learner answers or scoring. Incident examples extend the demonstration; they do not add scored professional courses.

The local Qwen3.5-9B model selects eligible report facts for the selected aircraft. A deterministic validator checks supported claims, identity and timing; the UI renders the accepted report summary. Sources opens supporting reports for that answer and cutoff. Recent reports may contain newer arrivals. The driver controls movement, not the model. The event reports are authored; model evidence selection is performed at request time. Failed or invalid answers are not replaced by scripted ones.

Verification and limitations

All three short lessons reached debrief in earlier native iOS Simulator acceptance. The collision/landing extension passed 229 backend tests, 60 Unity checks and a native build/install. Its two targeted recordings displayed four actual accepted answers in 10.203–17.736 seconds. A separate initial cold-model request took 50.556 seconds and exceeded the app deadline; its failure is retained. The four successful requests are functional examples, not an accuracy benchmark. See outputs/checkpoint1/accident-acceptance.json.

The immediate weather extension passed 231 backend tests, 69 Unity checks, native export and Xcode build. Rain/snow/daylight changes were visually checked in the native viewer. The weather captures use a private 30× inspection profile with question/teaching pauses disabled; they add no new assistant-response acceptance claims. See outputs/checkpoint1/weather-acceptance.json.

The earlier frozen M1 study used 40 distinct turns, 17 families, four scenarios and three context conditions, with images off. Full-context scores were Qwen3.5-9B 24/40, Qwen3-VL-4B 16/40 and deterministic baseline 16/40. Tracking-interruption context did not improve scores in that setup. Do not describe these as new benchmark results for the current interface.

Realism

Describe occupied stands and delayed services as operational disruptions; wildlife and dropped loads as recognised hazards; aircraft contact/fire as abnormal cases; and a damaging landing as an exceptional emergency example. These are qualitative categories, not estimated Heathrow occurrence rates. The scenarios are presented separately with time scaling within each. The airport geometry, local circuit, incident animations and response timing are authored. They are not validated aircraft dynamics, real-time Heathrow traffic or an accident reconstruction. Rain, snowfall and a late-afternoon-to-night interval are now visual settings driven by external source time. They do not model braking, accumulation, de-icing or operational visibility. Sunrise/full-day profiles are not implemented.

External driver access

The source is included in the existing Checkpoint 1 GitHub branch. The video shows its effects rather than a console. After the local model, Unity/Xcode and app are set up, run from the repository folder:
.venv-candidates/bin/python -m backend.training --exercise late_arrival --mode demo --seed 17

Add --environment rain, snow or dusk (one setting per launch) to show visual conditions. The same source clock controls precipitation and light; these settings do not change aircraft performance or create weather reports.

Use --mode lesson for three scored checkpoints, or --mode continuous for the hour at normal speed. One service runs on port 8767; the model and driver stay on the Mac and the simulator is the viewer. A clone alone does not install the model or Apple/Unity tooling. See docs/TRAINING_DRIVER.md and docs/course/TEAMMATE_SETUP.md. Phone suitability

ApronLens is positioned as portable scenario practice and review for learners, not an operational control workstation. The phone suits a focused flight/report/checkpoint task; a tablet or larger display is the recommended format for a broader traffic overview. This is a design recommendation, not a completed controller-usability finding. Checkpoint 3 should compare phone and larger-screen use with representative learners. Do not claim that Heathrow controllers routinely control traffic on smartphones. ENAC’s tablet-capable ELSA provides a training precedent; it does not validate this app. See HEATHROW_SCENARIO_BASIS.txt.
