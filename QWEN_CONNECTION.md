# Qwen connection: coordinator reasoning and event history

The Unity app now calls the locally installed **Qwen2.5-VL-3B-Instruct** model.
The model runs on the Mac; the Android app remains the AR interface. No model
weights are packaged into the APK. This is a fictional coordination research
prototype, with no operational airport feed or movement authority.

## Use the app

1. Start the Mac service from this project folder:
   `bash scripts/start_qwen_server.sh`
2. Open the Unity `DesktopReplay` scene and enter Play mode. The editor reads
   the local connection token automatically. Select an aircraft and checkpoint.
3. Open **Why → Qwen → Explain**. The app pauses the replay, renders the
   synthetic scene, and requests an explanation for that aircraft and time.
4. Read the model answer separately from **Deterministic baseline**. Open the
   evidence-ID buttons to inspect the original reports and their timestamps.
   **History** filters by selected flight unless **All flights** is chosen.
5. Changing the aircraft or replay time hides the old answer. Generate again to
   get an answer for the new context. A failed connection preserves the reports
   and baseline rather than replacing them with a fabricated model response.

The first server start creates `work/qwen-server-token.txt`. Keep it local.
The service defaults to `http://127.0.0.1:8765`, accessible on this Mac only.
The server stays loaded between requests. Stop its process when finished.

## Android connection when ready

Install `outputs/milestone1/AirfieldCoordination-M1.apk` (version 1.3, build 4).
Phone tracking and networking still need the deferred physical-device check.

**USB option:** with USB debugging approved, forward the phone's port using
`adb reverse tcp:8765 tcp:8765`. Start the server with its default address. In
**More → Model connection**, use `http://127.0.0.1:8765` and paste the token from
`work/qwen-server-token.txt`.

The bundled adb executable is:
`work/unity-editor/PlaybackEngines/AndroidPlayer/SDK/platform-tools/adb`.

**Wi-Fi option:** on a trusted shared network, start
`bash scripts/start_qwen_server.sh --host 0.0.0.0` and enter
`http://<Mac LAN address>:8765` plus the same token in the app. The Mac firewall
must permit the connection. This development build uses HTTP, not encrypted
transport; use only this fictional scenario. The token is stored locally in
app preferences and is not included in the APK or request logs.

## What the model receives

The production method is `pairwise-predicates-v5`, using the same local model
weights; no fine-tuning was performed. Qwen makes short Yes/No decisions about
flight/property membership, supplied current-state labels, and pairwise report
receipt times. Missing-evidence flags derive from the same decisions, so they
cannot independently contradict the selected records. All historical matching
records remain eligible for change-history queries.

The service receives the selected aircraft, checkpoint, structured query and a
synthetic Unity scene render. It independently loads time-eligible reports from
the scenario. **The production model uses text only**: that image contains no
answer-bearing service or plan evidence. It is decoded and hashed for audit,
with `imageUsedForInference=false`; it is not a phone-camera photo. The fresh
research evaluation includes a separate image negative-control condition.

Temporal status classification, source/value copying and sentence rendering
are deterministic. This constrained hybrid improves the evidence interface; it
is not proof that Qwen learned temporal state inference. Empty evidence produces
unknown without a model call. The deterministic answer baseline is not called
inside model inference, and never silently fills in a failed model answer.

Multi-frame motion understanding, visually necessary questions and longitudinal
retrieval remain research extensions in `RESEARCH_PLAN.md`.

## Claim support and temporal state

The pipeline produces **atomic claim selections** from Qwen predicate decisions.
Fact values, temporal statuses and source IDs are copied losslessly from records,
not generated by the model.
The service checks every field against the received evidence for the selected
aircraft and flight instance. It also checks the required claim set for the
explicit query type: latest report, current value, or change history. Unsupported,
incomplete, or malformed selections are withheld; they are not silently repaired.
The legacy evaluation parser still allows one extra `claim` JSON wrapper without
altering its contents; production does not ask the model to generate JSON.

Accepted selections use deterministic sentence templates. This fixes the old
citation bug within the supported typed schema: a stand claim cannot borrow a
baggage report's citation, and two facts cannot be merged into unverified prose.
It does **not** constitute a general natural-language entailment checker. The UI
identifies the result as Qwen-selected evidence and explains that templates
supply the wording. The deterministic baseline remains available separately.

The event engine now supports validity intervals, explicit supersession, future-
effective changes, conflicts, and flight/rotation identity. Receipt time governs
what was known; valid time and supersession govern what remains current. A late
older report cannot replace an explicitly superseding update. A superseded plan
does not revive when a replacement expires. TOBT is treated as an estimate,
never a movement clearance. Overall readiness remains unestablished by the demo.

The Android scene still contains the original M1 replay. The additional 12
scenario families are exercised in the evaluation harness, not an Android
scenario picker. The current app asks for the latest report; the service and
harness additionally support explicit current/change queries and properties.

## Evaluation and audit

The current paired fresh evaluation is in `outputs/reasoning_v2/REPORT.md`.
The method and source hashes were frozen before opening 32 fresh questions in
8 separately authored scenario families. The original prompt scored 9/32; the
new text-only selector scored 31/32, including 12/12 missing-evidence questions
and 8/8 change histories. The remaining failure selected an unrelated stand
claim for a route question and was withheld. The separate deterministic baseline
scored 32/32. No tuning followed these fresh results. Two of the 12 missing-evidence cases
used empty-context logic with no model call. The frozen legacy prompt has a
singular latest-event wording mismatch on a receipt-time tie; this is a
whole-system comparison, not an isolated causal test. Read `audit-notes.json`.

The scene-image negative control scored 10/32. Production had already been set
to text-only evidence decisions before the fresh run. This is evidence against
adding that irrelevant schematic to this report-query task, not against visual
reasoning on genuinely visual questions. No model weights were trained.

The fresh data was authored by a separate agent, not independently validated by
an aviation expert. Questions within families are correlated. Correct source
links/status labels are construction guarantees, and the completeness guard
checks a deterministic answer contract. Neither makes raw model errors correct.
Raw outputs, decision traces, all failures, protocol/source snapshots and the
separate baseline are preserved. See `development-history.json` for all five
development trials; the final one scored 23/24, including a retained latest-report
failure. Prior v1 results remain at `outputs/reasoning_v1/REPORT.md` unchanged.

The image condition is a deliberately non-diagnostic schematic negative control;
it cannot establish visual reasoning. A genuine spatial/temporal vision benchmark
with answer-bearing images remains a separate next step.

Local audit records in `work/qwen-requests.jsonl` contain model revision, tokens,
latency, evidence, raw claim selections, validation errors, decision prompts and
Yes/No scores, method version, and image hash. Scores are not calibrated confidence. Raw image bytes and connection secrets are not logged. Earlier development
responses remain in the audit. The previous free-prose citation limitation is
preserved in `outputs/milestone1/qwen-smoke-review.json` as historical evidence;
its response hash identifies the old answer rather than the new typed output.

## Reproduce verification

- Backend contract/regression checks (HTTP tests use a clearly identified test double):
  `.venv-qwen/bin/python -m unittest discover -s tests -v`
- Real model + Unity HTTP test: run the Unity editor in batch mode with
  `-executeMethod QwenIntegrationVerification.Run` **without `-quit`**, with the
  server already running. The method exits when its asynchronous checks finish.
- Build Android: `bash scripts/build_milestone1.sh`
- Verify package: `.venv-qwen/bin/python scripts/verify_android_build.py`

Results are saved in `outputs/milestone1`: `ui-verification.json`,
`qwen-integration-verification.json`, `qwen-response-13.json`, and
`qwen-response-14.json`. The two real-model cases test the late-report boundary
before and after receipt. The final production run accepted both answers at
13 and 14 seconds (2 accepted, 0 withheld) and rejected a stale answer after
rewind. This is a development integration check, separate from the frozen fresh
evaluation. Earlier withheld results remain in the audit/development record.

The Galaxy S24 layout test lives at `outputs/milestone1/s24/`. It renders actual
Unity UI at 1080 × 2340 with assumed 90 px top / 72 px bottom gesture-navigation
insets and density 3. The wireframe is an illustrative device shell, not a phone
capture. Touch-size and type-size checks use those explicit assumptions; actual
One UI settings, keyboard, Android font scaling and physical touch remain untested.


Implementation follows the installed Transformers interface and FastAPI model
lifespan pattern:

and [FastAPI lifespan documentation](https://fastapi.tiangolo.com/advanced/events/).
